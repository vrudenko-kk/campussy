# Campussy — навигационная карта кампуса

Mobile-first веб-приложение для навигации по кампусу Финансового университета по адресу: Москва, 4-й Вешняковский проезд, дом 4.

Пилот объединяет глобальную 3D-карту трех корпусов, поиск аудиторий и инфраструктуры, интерактивные поэтажные схемы и построение маршрута от точки, выбранной пользователем.

[Открыть публичный пилот](https://campussy-navigation.aleksandra-grab-91.chatgpt.site/)

> [!IMPORTANT]
> Это навигационный пилот, а не официальный план эвакуации. Геометрия, расстояния и часть привязок помещений требуют натурной проверки перед эксплуатацией.

## Возможности пилота

- mobile-first интерфейс для экранов от 360 пикселей и адаптация для компьютера;
- глобальная карта трех корпусов, общего входного блока, внутреннего двора, КПП и условного периметра кампуса;
- 3D-экструзия зданий по сохраненным контурам OpenStreetMap с локальной кликабельной схемой на случай недоступности внешней карты;
- начальный обзор на корпус 3 в направлении на юг и автоматическая смена ориентации при выборе корпуса;
- переход с глобальной карты напрямую к этажам выбранного корпуса;
- поиск по номеру, названию, категории и синонимам;
- рекомендации и история последних поисков, хранящаяся локально в браузере;
- самостоятельный выбор начальной и конечной точек;
- пешеходный маршрут от метро «Рязанский проспект» и обратно через Valhalla API;
- выбор этажа при нажатии на лифт или лестницу;
- действия «Маршрут отсюда» и «Маршрут сюда» при нажатии на аудиторию;
- расчет кратчайшего пути алгоритмом Дейкстры по этажам, лестницам, лифтам, переходам между корпусами и наружным участкам;
- линия движения на каждом задействованном этаже и отдельное отображение межэтажных и межкорпусных переходов;
- компактный режим навигации: карта и следующий шаг находятся в фокусе, подробный текст открывается отдельно;
- карточки аудиторий, главного входа, КПП, столовой, буфета, Coffix, библиотеки, спортзала, санузлов, лестниц и лифтов;
- поиск неподтвержденных помещений без построения ложного маршрута к ним.

## Границы MVP

Текущая версия — статическое клиентское приложение. Для запуска не нужны backend, база данных, регистрация или установка npm-пакетов.

В MVP не входят:

- Face ID, распознавание лиц и другие биометрические функции;
- обязательная авторизация и персональное расписание;
- автоматическое позиционирование пользователя внутри здания;
- гарантированный безбарьерный маршрут до полевой проверки входов, лифтов и препятствий;
- серверное API, административная панель и централизованная аналитика;
- синхронизация истории поиска между устройствами;
- физический инфомат — он рассматривается как возможный отдельный этап после проверки веб-версии.

## Быстрый запуск

### Требования

- Python 3 — для локального HTTP-сервера;
- Node.js 20.11 или новее — только для запуска тестов и подготовки релиза.

### Запуск приложения

Из корня репозитория выполните:

```bash
python3 -m http.server 4173 --directory dist
```

Откройте [http://localhost:4173](http://localhost:4173).

Не открывайте `dist/index.html` двойным щелчком: браузер может ограничить загрузку ES-модулей. Чтобы остановить сервер, нажмите `Ctrl+C` в терминале.

### Запуск в локальной сети

Чтобы открыть пилот на другом устройстве в той же Wi-Fi-сети:

```bash
python3 -m http.server 4173 --directory dist --bind 0.0.0.0
```

На macOS можно узнать локальный IP-адрес командой:

```bash
ipconfig getifaddr en0
```

На другом устройстве откройте адрес вида `http://192.168.x.x:4173`. Компьютер с сервером и второе устройство должны находиться в одной сети.

## Тестирование

Полный набор автоматических проверок:

```bash
node --test tests/*.test.mjs
```

Тесты проверяют:

- связность графа и наличие узлов у маршрутизируемых объектов;
- корректность маршрута от КПП через общий вход и внутренний двор;
- начало и конец линии у двери выбранной аудитории;
- межэтажные и межкорпусные переходы в обоих направлениях;
- отсутствие пересечений маршрута с чужими помещениями и внутренними стенами;
- геометрию 8-го этажа корпуса 3;
- зеркальность планов корпусов 1 и 2;
- блокировку маршрута к помещению без подтвержденной двери.

Перед публикацией обновите единый идентификатор статических ресурсов, затем повторно запустите тесты:

```bash
node scripts/version-assets.mjs
node --test tests/*.test.mjs
```

## Архитектура

Пилот намеренно не использует обязательный серверный контур. Интерфейс, данные, геометрия этажей и граф маршрутов разделены на независимые ES-модули.

```text
Браузер
├── index.html             оболочка приложения
├── styles.css             mobile-first интерфейс
├── app.js                 состояние, поиск и пользовательские сценарии
├── campus-map.js          глобальная 3D-карта и выбор корпуса
├── floor-map.js           SVG-план и визуальный маршрут
├── router.js              граф, Дейкстра и этапы маршрута
├── street-router.js       пешеходный API, уличный трек, тайм-аут и кэш
├── outdoor-data.js        метро, дорога, КПП и единая геометрия ограждения
├── campus-data.js         корпуса, этажи, объекты и связи
├── floor-plans.js         базовые планы кампуса
├── wing-plans.js          планы корпусов 1 и 2
└── wing-directory.js      справочник помещений корпусов 1 и 2
```

Ключевые принципы:

- геометрия отображения отделена от графа маршрутизации и связана с ним устойчивыми идентификаторами;
- одна и та же модель дверей и проходов используется для SVG и расчета пути;
- наличие помещения в поиске не означает наличие маршрута: нужна подтвержденная дверь и связь с графом;
- внешняя картографическая подложка не является критической зависимостью;
- клиент не содержит административных секретов и персональных данных;
- серверное API и управляемая публикация данных добавляются только после подтверждения пилота.

Подробнее: [архитектура пилота](docs/architecture.md).

## Состояние данных

### Кампус

Контуры трех корпусов, общего входного блока и КПП получены из OpenStreetMap через Nominatim и Overpass API и сохранены в проекте. Они используются для обзорной 3D-карты и не заменяют кадастровую документацию.

### Поэтажные планы

- корпус 1: этажи 1–5 восстановлены по предоставленным планам эвакуации и стенду; этажи 3–5 используют общий типовой план по исходному допущению;
- корпус 2: этажи 1–5 зеркальны соответствующим этажам корпуса 1; номера и назначения помещений сверяются со стендом корпуса 2;
- корпус 3: 1-й этаж восстановлен по описанию команды; этажи 2, 3, 4, 5, 7 и 9 используют подписанный план 2-го этажа, этажи 6 и 8 — план 8-го этажа; перенос шаблонов выполнен по указанию команды;
- неизвестные или неподтвержденные привязки явно помечаются и не участвуют в маршрутизации.

### Известные переходы

- корпус 1, этаж 2 → корпус 3, этаж 2 через Coffix;
- корпус 2, этаж 4 → корпус 3, этаж 3;
- корпус 1, этаж 5 → корпус 3, этаж 4;
- главный вход, этаж 1 → направо в корпус 1, налево в корпус 2;
- отдельный вход через корпус 1;
- КПП → общий главный вход между корпусами 1 и 2 → внутренний двор → вход в корпус 3 на 1-м этаже.

Все связи двусторонние. Метро связано с КПП пешеходным треком API; при недоступности API приложение предлагает повторить запрос. Внутренние маршруты считаются локально. Публичный демонстрационный сервер Valhalla подходит для пилота; для масштабирования потребуется собственный сервер или провайдер с согласованными лимитами.

Подробное происхождение данных и список допущений: [источники и качество данных](docs/data-sources.md).

## Ближайшие задачи

1. Провести натурную проверку дверей, проходов, лифтов и известных переходов между корпусами.
2. Сверить геометрию добавленных проходов из общего входного блока в корпуса 1 и 2.
3. Привязать к дверям помещения, которые сейчас доступны только в справочнике.
4. Проверить перенесённые шаблоны корпуса 3 на каждом этаже.
5. Расширить мобильную регрессию и эталонный набор полевых маршрутов.
6. Согласовать владельца данных и регламент публикации обновлений.

## Roadmap после пилота

- версионируемые JSON/GeoJSON либо PostgreSQL/PostGIS для карт и графа;
- API каталога, поиска и маршрутов с сохранением текущей клиентской модели;
- ролевая административная панель и процесс «черновик → проверка → публикация»;
- официальные интеграции с расписанием и справочником подразделений;
- безбарьерный режим после обследования инфраструктуры;
- мониторинг ошибок, производительности и качества данных;
- PWA, QR-ссылки и синхронизация истории — при подтвержденной пользовательской ценности;
- физический инфомат как дополнительная точка доступа к тому же веб-приложению.

## Правила изменения карт

1. Для нового плана укажите источник, дату, ответственного и статус проверки.
2. Не включайте помещение в маршрутизацию без подтвержденной двери и связи с коридорным графом.
3. Не публикуйте фотографии с подписями, печатями, отражениями людей или другими лишними данными.
4. После изменения геометрии обязательно запустите все тесты.
5. Проверьте маршрут в обоих направлениях и на мобильной ширине от 360 пикселей.
6. Перед публичным релизом обновите версии ресурсов командой `node scripts/version-assets.mjs`.
